# Multi-Vendor Commerce Platform

A production-oriented multi-vendor e-commerce and order orchestration platform
built to model real marketplace workflows including vendor split-orders,
inventory reservations, payments, fulfillment, refunds, and audit history.

This project is being developed as a flagship full-stack software engineering
portfolio project.

---

## Project Goal

Build a marketplace where multiple vendors can sell products through one
platform while customers experience a unified checkout.

A single customer order may contain products from multiple vendors.

Internally, the platform splits fulfillment responsibility by vendor so that
each vendor can independently process its portion of the order.

Example:

```text
Customer Order #1001
│
├── Vendor A Order
│   ├── Shirt × 2
│   └── Pants × 1
│
└── Vendor B Order
    └── Shoes × 1
```

This allows independent:

- fulfillment
- shipment
- cancellation
- refund handling
- vendor ownership enforcement

without losing the customer's single-order experience.

## Architecture

The application begins as a modular monolith.

```text
Customer / Vendor / Admin
            │
            ▼
        Next.js Web
            │
            │ REST API
            ▼
         NestJS API
            │
            ▼
        PostgreSQL
```

A modular monolith is intentionally used before considering microservices.

The goal is to maintain strong domain boundaries without introducing
distributed-system complexity before it is justified.

## Core Commerce Model

The most important modeling decision is separating the customer's parent order
from each vendor's fulfillment responsibility.

```text
Order
│
├── VendorOrder
│   └── OrderItems
│
└── VendorOrder
    └── OrderItems
```

This allows:

```text
Vendor A → DELIVERED
Vendor B → PROCESSING
```

to exist simultaneously.

The platform can therefore support partial fulfillment without overwriting
vendor-specific history.

## Important Data Invariants

The system is designed around rules such as:

- inventory cannot become negative
- order quantities must be positive
- monetary amounts cannot be negative
- external payment identifiers must not be processed twice
- vendor ownership boundaries must be preserved
- historical orders must retain purchase-time values
- inventory reservations must be concurrency-safe
- refunds cannot exceed the refundable paid amount
- shipment history must be preserved
- audit records are append-only

These rules will be enforced through a combination of database constraints,
transactions, locking, application validation, authorization, and automated
tests.

## Engineering Principles

This project prioritizes:

1. Explicit business rules over screen-first development.
2. Database integrity over relying only on application validation.
3. Clear module ownership.
4. Vendor data isolation.
5. Transactional consistency.
6. Historical correctness.
7. Idempotent external integrations.
8. Automated testing of important business rules.
9. Production-oriented security and observability.
10. Architecture complexity only when justified.
